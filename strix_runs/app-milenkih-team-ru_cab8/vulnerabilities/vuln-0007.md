# Broken object-level authorization on notifications collection allows any user to reassign someone else's notification (forged in-app notifications)

**ID:** vuln-0007
**Severity:** LOW
**Found:** 2026-09-12 15:28:54 UTC
**Target:** https://app.milenkih-team.ru (PocketBase API, `notifications` collection)
**Endpoint:** /api/collections/notifications/records/{id}
**Method:** PATCH
**CWE:** CWE-639
**CVSS:** 3.5
**Confidence:** High
**Fix Effort:** Low

## Description

The PocketBase `notifications` collection accepts an UPDATE from any authenticated user that rewrites the `recipient` field to a different user's ID. A plain (non-moderator) account can therefore take a notification it owns, replace its text with arbitrary content, and re-address it to any other user — including moderators. Because the client lists notifications by `recipient = <my id>`, the forged record is displayed inside the victim's notification feed, impersonating official in-app messages.

## Impact

An authenticated low-privilege user can inject arbitrary, attacker-controlled text into another user's in-app notification feed. Notifications are a trusted, branded channel in this application (membership expiry warnings, training reminders, broadcast messages) and the card renders the record's own `title`/`body` with a click action, so a forged card is indistinguishable from an official one. This supports targeted phishing/social engineering (e.g. "оплатите абонемент по ссылке", "ваша запись отменена") and can be aimed at moderators, who hold administrative functions. It also permits one-off corruption of a victim's notification state and, in combination with the notification deep-link handler, attacker-chosen navigation targets for social notifications (`meta.collection` / `meta.postId`). The write is unauthenticated-to-authorization-bypass: no moderator role and no ownership of the target user is required.

## Counterevidence

Actively tested the case against the finding. (1) Considered that the server may silently ignore the `recipient` change: refuted — the 200 response body itself returned `"recipient":"z7piq9643k5995x"`, and the subsequent 404 on read-back confirms the record moved out of the attacker's ownership scope (had the field been ignored, the record would still have been readable by the attacker). (2) Considered a server-side notification queue, approval flow or superuser-only write path: no such gate blocked the write; the same collection already grants the caller create rights for self-addressed records, so the write path is a normal member capability. (3) Considered a global PocketBase rule misconfiguration: refuted by the control tests — foreign comment PATCH is 404, foreign DELETE is 404, foreign-recipient POST is 400, i.e. only the notifications UPDATE rule is loose. (4) Considered XSS via the injected fields: `NotificationCard` renders `title`/`body` through `PostContentHtml`, which sanitizes to an allowlist, so the impact is spoofing rather than script execution and no XSS is claimed. (5) Considered whether the card is really shown to the victim: the list filter is `recipient = {:uid}`, so the forged record is in scope for the victim, but the attacker cannot read the victim's feed (404 on foreign ids); this last hop was not visually confirmed from the victim's session, which is the sole remaining proof gap and is why confidence on the *displayed* effect is stated as high-on-write / not verified-from-the-victim-side. (6) A deliberately attempted escalation — creating a notification for a foreign recipient directly — was rejected with 400, so the finding is limited to the update path.

## Confidence Rationale

The write primitive was executed live against the production API and verified three independent ways: the 200 response echoing the new `recipient`, the attacker's subsequent 404 on the same record, and the failing control tests on neighbouring collections and on the delete/create paths. The only element not directly observed is the rendered card inside the victim's own session (the attacker's token cannot read another user's notifications, by design); the client code path that selects and renders it (`listNotifications` filtered by `recipient`, `NotificationCard` rendering `title`/`body`) is confirmed from source.

## What Would Change This Severity

Confirmation that the forged card is rendered inside the victim's notification feed from the victim's own session would leave this as a high-severity spoofing/authorization defect; evidence that a moderator also acts on the forged card's click action (e.g. a stored action that triggers a privileged server operation) would raise it to critical, while evidence that the notifications list is only ever populated server-side for the victim (making the reassigned record unreachable) would lower it to medium.

## Technical Analysis

PocketBase enforces authorization at the collection level through API rules. For `notifications`, the create rule binds `recipient` correctly (a plain user cannot create a record addressed to somebody else — every attempt returned HTTP 400), and the delete rule is ownership-scoped. The **update rule, however, does not pin `recipient` to the existing/authenticated owner**, so a single-field `PATCH` can move an existing record to another user id.

The write primitive is trivially reachable because the same collection granted the attacker create rights for records addressed to themselves. `client/src/services/notifications.js:123` (`maybeNotifySessionsLeft`) creates notifications client-side with a caller-supplied `recipient`, which is why a normal user account can seed a record it owns and then re-address it.

Observed sequence against the live API with the account's own token:
1. `POST /api/collections/notifications/records` with `{"recipient":"<own id>","title":"...","body":"..."}` → `200`, record created.
2. `PATCH /api/collections/notifications/records/<id>` with `{"recipient":"<other user id>"}` → `200`, and the response body echoed `"recipient":"<other user id>"` together with the attacker-chosen `title`/`body`.
3. Immediately afterwards the attacker's own `GET /api/collections/notifications/records/<id>` → `404`, while the reassignment response had returned the record milliseconds earlier — i.e. the record persisted with the new owner and left the attacker's read scope.

Control experiments show this is collection-specific and not a blanket PocketBase misconfiguration:
- `PATCH /api/collections/comments/records/<foreign id>` → `404` (comments update IS ownership-scoped).
- `DELETE /api/collections/notifications/records/<foreign or nonexistent id>` → `404`, while deleting an owned record → `204` (delete IS ownership-scoped).
- `POST` with a foreign `recipient` → `400` (create IS bound to the caller).

Rendering path: `src/features/notifications/NotificationCard.jsx:578-591` renders `notification.title` and `notification.body` through `PostContentHtml`, and `src/features/notifications/NotificationCard.jsx:596-604` renders `badge_text` and a click-action button. `PostContentHtml` sanitizes with an allowlist (`toDisplayHtml` → `sanitizePostHtml`), so the content lands as text/markup-limited HTML rather than script — this is a spoofing/authorization defect, not XSS. The victim's feed is populated by `src/services/notifications.js:33-37` (`listNotifications`, `filter: recipient = {:uid}`).

## Proof of Concept

1. Authenticate as any ordinary (non-moderator) user and note your own user id and another user's id (user ids are enumerable by any authenticated user through `GET /api/collections/users/records`).
2. Create a notification record addressed to yourself so you own it: `POST /api/collections/notifications/records` with `{"recipient":"<your id>","title":"...","body":"...","is_read":false}`. Expect HTTP 200 and an `id` in the response.
3. Replace the recipient with the victim's user id in a single-field update: `PATCH /api/collections/notifications/records/<id>` with body `{"recipient":"<victim id>"}`. Expect HTTP 200 and a response body whose `recipient` is now the victim while `title`/`body` remain attacker-controlled.
4. Confirm the reassignment persisted by reading the record back with your own token: `GET /api/collections/notifications/records/<id>` returns HTTP 404 — the record has left your ownership scope.
5. Log into the victim account (or observe its notification list) and confirm the forged card with the attacker-supplied title/body appears in the feed, since `listNotifications` queries `recipient = <victim id>`.

````bash
# 1. Create a notification you own (attacker = low-privilege user, no moderator role)
curl -s -X POST 'https://app.milenkih-team.ru/api/collections/notifications/records' \
  -H "Authorization: $TOKEN" -H 'Content-Type: application/json' \

# 2. Re-address it to the victim (single-field PATCH)
curl -s -X PATCH 'https://app.milenkih-team.ru/api/collections/notifications/records/<NOTIFICATION_ID>' \
````

## Remediation

1. Tighten the `notifications` update API rule so that a record can only be updated by the authenticated user it belongs to and so that the `recipient` field cannot change: for example require `recipient = @request.auth.id` on the update rule and keep the "current recipient" equality requirement, so that any update whose new `recipient` differs from the stored one is rejected.
2. Serve the field value through a server-side guard as well as the rule: add an `onRecordUpdateRequest` hook on `notifications` that throws a `ForbiddenError` when `e.record.get('recipient') !== e.record.original().get('recipient')` for non-superuser callers, mirroring the existing `pb_hooks/users_access_guard.pb.js` pattern already used for the `users` collection.
3. Restrict client-side creation of notifications. Privileged notification types (membership, training, broadcast) should be produced server-side by the existing hooks rather than by `client/src/services/notifications.js:123` (`maybeNotifySessionsLeft`), which lets any caller choose a `recipient`. If client-side creation must remain, bind `recipient` to `@request.auth.id` in the create rule.
4. Treat notification `title`/`body`/`badge_text` as trusted branding: keep them immutable to non-superusers (consider excluding them from the update rule, or restricting updates to the `is_read` field) so the feed cannot be used as a phishing surface.
5. Re-run authorization checks across the remaining collections with the same matrix (create/update/delete × own/foreign/nonexistent) — comments, gallery and tournament comments, posts, tournament_posts, trainings, products, achievements and the audit/log collections — since the notifications update rule shows the rules were written per-collection and at least one was left loose.

## Assumptions

Requires only a valid low-privilege authenticated session; no moderator role, no elevated privilege and no victim interaction are needed. The attacker must know a target user id, which any authenticated user can enumerate from `GET /api/collections/users/records`. All test records created during validation were deleted afterwards.
