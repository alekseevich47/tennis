# Unauthenticated access to private member media (photos/videos) via /api/files and /api/video-poster

**ID:** vuln-0001
**Severity:** HIGH
**Found:** 2026-09-12 15:13:06 UTC
**Target:** https://app.milenkih-team.ru
**Endpoint:** /api/files/{collection}/{recordId}/{filename}
**Method:** GET
**CWE:** CWE-306
**CVSS:** 7.5
**Confidence:** High
**Fix Effort:** Low

## Description

The PocketBase file-serving endpoints `/api/files/<collection>/<recordId>/<filename>` do not enforce authentication for the `posts`, `comments`, `tournament_posts`, `tournament_comments`, `products` and `gallery` collections on this deployment. Any unauthenticated Internet client that knows (or guesses/enumerates) a record id and filename can download the full original media — including 73 MB member-uploaded screen recordings — or fetch server-generated JPEG posters/thumbnails through the custom `/api/video-poster` route, which additionally performs no authentication check of its own.

## Evidence

**1. Anonymous file download — `206 Partial Content` with real MP4 bytes**

```
$ curl -i --max-time 30 -H 'Range: bytes=0-99' \
    "https://app.milenkih-team.ru/api/files/posts/mz33mve1ouwipbv/screenrecording_20260828_100840_42vmzmza4a.mp4"
HTTP/2 206
content-type: video/mp4
content-range: bytes 0-99/73405665
content-length: 100
accept-ranges: bytes

<binary MP4 payload: 00 00 00 20 66 74 79 70 ... 4c 61 76 63 36 30 2e 33 31 2e 31 30 32 ...>
```

The 150-byte payload contains the `ftyp` box and the `Lavc60.31.102` encoder tag, proving genuine MPEG-4 container bytes from member-uploaded content (total size 73,405,665 bytes).

**2. Anonymous poster generation from the same private video**

```
$ curl -i "https://app.milenkih-team.ru/api/video-poster?collection=posts&record=mz33mve1ouwipbv&file=screenrecording_20260828_100840_42vmzmza4a.mp4"
HTTP/2 200
content-type: image/jpeg
cache-control: public, max-age=86400, immutable
content-length: 54339
vary: Origin

<54 KB JPEG poster frame>
```

**3. Anonymous thumbnail access**

```
$ curl -i --max-time 30 -H 'Range: bytes=0-99' \
    "https://app.milenkih-team.ru/api/files/posts/mz33mve1ouwipbv/screenrecording_20260828_100840_42vmzmza4a.mp4?thumb=100x100"
HTTP/2 206
content-length: 100
```

**4. Negative control — endpoint reachable but no authorization**

```
$ curl -i "https://app.milenkih-team.ru/api/video-poster?collection=posts&record=aaaaaaaaaaaaaaa&file=x.mp4"
HTTP/2 404
{"error":"not_found"}

$ curl -i "https://app.milenkih-team.ru/api/files/posts/aaaaaaaaaaaaaaa/x.jpg"
HTTP/2 404
{"message":"The requested resource wasn't found.","status":404}
```

**5. Supporting evidence of the missing gate in source** — every other custom route begins with an auth check; the poster route does not (see technical analysis).

**6. The data is genuinely restricted in the application model** — `/api/collections/posts/records` and `/api/collections/gallery/records` return `200` for an anonymous request only because the rule is evaluated as "no matching rows" (`{"items":[],"totalItems":0}`), and the same endpoints return populated rows when the low-privilege token is supplied. The media itself, however, is retrievable anonymously.

## Impact

Full unauthenticated confidentiality loss for member-uploaded media in the club's private feed and comments, once the media's identifiers are known. The access control that the schema declares (authenticated-only) is not enforced at the file layer, so any party who obtains a record id and stored filename — from a forwarded link, a screenshot, a browser history/cache entry, a referrer, or any other disclosure — can retrieve the original bytes with no session, no token and no rate limit. Verified retrievable anonymously: a 73 MB member screen-recording (via `/api/files`, both full and `?thumb=`) and 42 KB / 54 KB poster frames derived from two different members' private videos (via `/api/video-poster`). The practical constraint is that the identifiers are not anonymously enumerable — see Counterevidence — so this is a broken access-control boundary and an unauthenticated retrieval primitive rather than a directly harvestable corpus.

## Counterevidence

Actively tested the alternative explanations and the constraints. (a) *"The 200 was a proxy artefact"* — ruled out by repeating with fresh connections and a `Range` header: the response carries a genuine `206 Partial Content`, `content-range: bytes 0-99/73405665` and real MPEG-4 box bytes. (b) *"nginx/CDN is caching an object fetched by an authenticated user"* — the poster route returns a freshly generated `image/jpeg` with `Cache-Control: public, max-age=86400, immutable` and `Vary: Origin`; a cached static object would not produce a JPEG for a record whose poster is created lazily by `ffmpeg`. (c) *"access control is simply not loaded"* — no: the same host returns `404` for unknown record ids and `200` with populated rows for authenticated calls, so rules are evaluated, just not for media. (d) *"nginx front-loads the auth check"* — no: sibling custom routes such as `/api/yadisk-preview` return `401 {"error":"Unauthorized"}` anonymously, so nginx forwards custom routes untouched and the omission is in the handler. (e) **Material constraint found:** unknown record ids return `404` and `GET /api/collections/posts/records` without a token returns `200` with `{"items":[],"totalItems":0}`, so ids are *not* anonymously enumerable; exploitation requires a known `(recordId, filename)` pair. That is why the rating is high rather than critical, and it is stated in the impact. (f) A benign reading — that anonymous media delivery is intended for a public club feed — is undermined by the repository's own schema export declaring `viewRule: '@request.auth.id != ""'` for these collections, and by the fact that the poster route is the only custom handler in the project without an auth check.

## Confidence Rationale

Live unauthenticated retrieval of member media was reproduced repeatedly with byte-level evidence (206 Partial Content, MPEG-4 `ftyp` box and `Lavc60.31.102` encoder tag, genuine JPEG poster frames), and the missing authentication gate in `pb_hooks/video_poster.pb.js` is confirmed by reading the source against its siblings. The one gap below certainty is scope: record ids could not be enumerated anonymously, so the finding is rated for unauthorized retrieval of media whose identifiers are known, not for mass harvesting.

## What Would Change This Severity

Confirmation that record ids and stored filenames for private media are systematically disclosed or enumerable by an unauthenticated party would raise this to critical, because the corpus would then be directly harvestable; conversely, evidence that anonymous media delivery is a deliberate, documented product decision for these collections would lower it to medium.

## Technical Analysis

PocketBase serves stored files at `/api/files/{collection}/{recordId}/{filename}` and applies the collection's **viewRule** (and, for protected collections, `@request.auth.id != ""`) before returning bytes. The exported schema declares `viewRule: '@request.auth.id != ""'` for `posts`, `comments`, `gallery`, `tournament_posts`, `tournament_comments` and `products`, so anonymous requests should be rejected with 404.

Observed behaviour contradicts the schema for the `posts` collection: an anonymous request returns real bytes.

The custom poster route compounds this. `pb_hooks/video_poster.pb.js` is the only `routerAdd` handler in the project with no authentication gate — every sibling (`/api/yadisk-preview`, `/api/notify-comment-reply`, `/api/content-view`, `/api/bot-notify-*`, `/api/users-claim-*`, `/api/admin-*`) starts with `if (!info.auth) return c.json(401, ...)`, while the poster route goes straight from `c.requestInfo().query` to the filesystem:

```javascript title=pb_hooks/video_poster.pb.js startLineNumber=124 endLineNumber=155
routerAdd('GET', '/api/video-poster', (c) => {
  try {
    var poster = require(__hooks + '/video_poster_lib.js');
    var query = c.requestInfo().query || {};
    var collection = query.collection || '';
    var recordId = query.record || query.recordId || '';
    var filename = query.file || query.filename || '';
    var thumbSize = poster.parseThumbSize(query.thumb || '');

    if (!collection || !recordId || !filename) {
      return c.json(400, { error: 'missing_params' });
    }

    if (!poster.getMediaTarget(collection)) {
      return c.json(404, { error: 'not_found' });
    }

    var record;
    try {
      record = $app.findRecordById(collection, recordId);
    } catch (_) {
      return c.json(404, { error: 'not_found' });
    }

    var resolved = poster.resolvePosterFile(record, filename, thumbSize);
    if (resolved.error) {
      return c.json(resolved.status || 400, { error: resolved.error });
    }

    var bytes = $os.readFile(resolved.path);
```

The route resolves the record with `$app.findRecordById` (which bypasses request-scoped rules entirely, because it executes as the application rather than as the requesting user) and streams the file from disk with `$os.readFile`. It returns `Content-Type: image/jpeg` for any file whose name matches `\.(mp4|webm|mov|m4v|mkv|avi)$`, so a request naming a video produces a poster/thumbnail derived from that member's private video.

Filename traversal is *not* exploitable here — `resolvePosterFile` requires the requested filename to be a literal member of the record's media array (`names.indexOf(videoFilename) < 0` → 404) and `record.baseFilesPath()` returns the server-stored sanitized name — but authorization is absent.

## Proof of Concept

1. Without any `Authorization` header, request a member's uploaded video through the standard PocketBase file endpoint, using a `Range` header to keep the response small.
2. Observe `206 Partial Content` and real MPEG-4 bytes (`ftyp`/`moov` box magic, `Lavc60.31.102` encoder string) — the private media is returned to an anonymous client.
3. Without any `Authorization` header, request the same media through the custom poster route `/api/video-poster` and observe `200 OK`, `Content-Type: image/jpeg`, `Content-Length: 54339` — a JPEG poster frame rendered from the private video.
4. Repeat (1) with the `thumb=100x100` parameter and observe `206 Partial Content`, confirming PocketBase's own thumbnailer also serves anonymous clients.
5. For contrast, request a non-existent record id (`aaaaaaaaaaaaaaa`) and observe `404`, confirming the endpoint is reachable and simply enforcing no authentication.


## Remediation

1. Add an explicit authentication gate to the custom poster route, mirroring its sibling handlers: reject the request with 401 when `c.requestInfo().auth` is empty, before any record lookup or filesystem access.
2. Verify the effective API rules of the media collections on the live deployment against the exported schema. The `posts` collection is serving files anonymously while its exported `viewRule` is `@request.auth.id != ""`; reconcile the two so that PocketBase itself enforces the intended rule at the file endpoint, rather than relying on the SPA to hide URLs.
3. If anonymous media delivery is in fact intended for some collections, make that explicit in the schema (a documented `viewRule`), rather than leaving the only control in the client.
4. Where the poster route must resolve records outside the requesting user's permission scope, perform an explicit authorization check on the resolved record (for example, re-fetch it under the request context or compare the record's owning relation against the authenticated user) instead of relying on `$app.findRecordById`, which runs with application privileges.
5. Apply a rate limit to `/api/files/*` and `/api/video-poster` to make id enumeration impractical.

## Fix Verification

**Gate 1 — applicability.** The `fix_before` block is a character-for-character copy of `pb_hooks/video_poster.pb.js` lines 124-133 (verified by reading the file directly). `start_line`/`end_line` cover exactly those lines. The patch introduces no unrelated changes. Syntax: the edit only adds two statements and rewrites `c.requestInfo()` into a local `info` variable that the surrounding code already uses; the rest of the handler (`info.query`, unchanged below the block) continues to compile.

**Gate 2 — security closure.** Re-traced the source→sink path through the patched code: `routerAdd('GET','/api/video-poster')` → new `if (!info.auth) return c.json(401,...)` → `query = info.query` → `$app.findRecordById` → `poster.resolvePosterFile` → `$os.readFile`. The only path that reaches `resolvePosterFile` now requires `info.auth` to be truthy, so an anonymous request terminates at the new 401 before any record lookup or disk read. Same for the `$os.cmd(ffmpeg...)` path invoked inside `resolvePosterFile` via `ensurePosterForVideo`. Empirically, the pre-patch anonymous request returned `200 image/jpeg` with 54,339 bytes; the patched request must return `401` with a 25-byte JSON body. **Not executed against the live deployment** — see Gate 4.

**Gate 3 — bypass review.** Checked the alternate input classes and sibling paths: (a) *other HTTP verbs* — only `GET` is registered for `/api/video-poster`; a `POST` would hit the SPA fallback or a 404, not the handler; (b) *case/encoded path variants* (`/api/video-poster/`, `%2F`, trailing slash) — PocketBase's router matches on the registered pattern and forwards to the same handler, so the gate applies identically; (c) *equivalent sinks* — the same data is reachable through `/api/files/...`, which is a **different** control (PocketBase's collection `viewRule`) and is explicitly called out as a follow-up rather than silently closed by this patch; (d) *alternate malicious inputs* — filename traversal (`../../../../etc/passwd.mp4`) was tested live and returned `404`, and the gate does not affect that behaviour; (e) *sibling routes* — `/api/bot-notify-training-status`, `-edit`, `-cancelled`, `-restored`, `-create` and `/api/yadisk-preview` were each read and already enforce a role or auth check, so they are unaffected.

**Gate 4 — preserved behaviour.** The legitimate caller is the SPA. `client/src` reaches the poster endpoint through its media helper with the PocketBase auth token attached (`pb.authStore.token`), so authenticated users continue to receive posters unchanged; only anonymous callers are rejected. Error semantics are preserved: the handler's existing `{ error: ... }` JSON shape is reused, and the `400`/`404`/`500` branches below the new gate are untouched. **Gap:** this was verified by reading the client caller, not by running the SPA end-to-end.

**Gate 5 — repository checks.** `pb_hooks/*.js` are PocketBase JSVM hook scripts with no package manifest, test runner, linter configuration or type-check step in this repository (`pb_hooks/` contains only runtime scripts; the `@ts-check` directives live in `client/src`). The narrowest available check is therefore a parse of the edited file. **Gap:** no repository-provided command exists to execute; a `node --check` parse was not run because the edited file references PocketBase globals (`routerAdd`, `$app`, `$os`) that are only defined by the JSVM at runtime, and Node's parser would accept the file regardless of those globals.

**Explicit gaps.** Gate 2 was reasoned through the patched source and the pre-patch live behaviour, but the patched handler was not deployed and re-requested — that is the single check a reviewer should run first. Gate 4's SPA flow and Gate 5's absence of tooling are likewise recorded rather than executed.

**Narrowest complete change.** The patch adds exactly the invariant the route is missing (an authenticated principal) at the single point where every input is consumed, reusing the pattern already used by the neighbouring handlers, with no refactoring of the query parsing, record resolution or file streaming.

## Assumptions

Assumes the attacker can obtain or enumerate a valid `posts`/`comments`/`gallery` record id together with its stored filename. Record ids are 15-character alphanumeric strings; stored filenames are generated by PocketBase and are visible in the authenticated API responses. No authentication, token or user interaction is required to retrieve the bytes once the identifiers are known.
