# Broken function-level authorization in /api/bot-notify-training allows any member to send spoofed moderator notifications

**ID:** vuln-0002
**Severity:** MEDIUM
**Found:** 2026-09-12 15:13:51 UTC
**Target:** https://app.milenkih-team.ru
**Endpoint:** /api/bot-notify-training
**Method:** POST
**CWE:** CWE-862
**CVSS:** 4.3
**Confidence:** High
**Fix Effort:** Trivial

## Description

The custom PocketBase route `POST /api/bot-notify-training` authenticates the caller but never verifies that they are a moderator, and it accepts the "acting as moderator" flag and the list of affected members directly from the request body. Any authenticated low-privilege club member can therefore make the club's MAX bot send moderators a message in the moderator voice, naming an arbitrary other member as the subject of a booking change that never happened.

## Evidence

**1. Live request as a plain `user` — the spoofed moderator broadcast is accepted**

```
$ curl -i -X POST "https://app.milenkih-team.ru/api/bot-notify-training" \
    -H "Authorization: <low-privilege user token>" \
    -H 'Content-Type: application/json' \
    -d '{"event":"unbook","userIds":["40z6k2wbrnw17wo"],"trainingId":"qs808160ey9ib5q","actorId":"hqd42tv9h085bk5","actorIsModerator":true,"totalBookedCount":0}'

HTTP/2 200
{"success":true}
```

The token belongs to user `hqd42tv9h085bk5` whose record has `"role":"user"`. The body sets `actorIsModerator: true` and names a *different* member (`40z6k2wbrnw17wo`) as the target.

**2. Resulting message text delivered to every moderator's MAX chat**

```
const isModAction = actorIsModerator && (userIds.length > 1 || userIds[0] !== actorId);
if (event === 'unbook') {
  if (isModAction) {
    text = 'Модератор *' + actorName + '* снял ' + namesStr + ' с ' + typeGen + suffix;
  }
}
```

With the payload above this evaluates to *"Модератор **Николай Кабенюк** снял **Илья Миленький** с тренировки ... Всего записано: 0."* — a fabricated moderator action naming another member, sent to every moderator.

**3. Source control point — authentication without authorization (lines 35-44)**

```
35:  const actorId = body.actorId;
36:  const actorIsModerator = !!body.actorIsModerator;
37:  const totalBookedCount = body.totalBookedCount;
38:
39:  if (!event || !userIds.length || !trainingId || !actorId || totalBookedCount == null) {
40:    return c.json(400, { error: 'Missing required fields' });
41:  }
42:  if (actorId !== auth.id) {
43:    return c.json(403, { error: 'Forbidden' });
44:  }
```

Only `actorId` is bound to the authenticated identity. `actorIsModerator`, `userIds`, `totalBookedCount` and `event` are taken verbatim.

**4. Sibling handlers prove the correct pattern exists**

The other five `bot-notify-*` routes (`-status`, `-edit`, `-cancelled`, `-restored`, `-create`) all contain `if (auth.getString('role') !== 'moderator') return c.json(403, ...);`. Only this one omits it.

**5. Delivery is real, not logged-only**

`botlib.js` `notifyModerators` → `sendBotMessage` → `$http.send({ method:'POST', url:'https://botapi.max.ru/messages?user_id=' + Number(maxId), ... })`, with recipients selected by `role = "moderator" && max_id != ""`. The global setting `training_booking_enabled` is `true`, so the message is sent, not skipped.

## Impact

Moderators — the club's trusted operators — receive attacker-controlled messages that appear in the application's own moderator voice and are indistinguishable from genuine operational notifications. An attacker can fabricate booking/cancellation events attributed to real members, name any member as the subject, and control the reported booking total. This is a trust and disruption issue rather than a data breach: moderators acting on fabricated booking or cancellation reports may contact or penalise the wrong member, and repeated calls are unbounded, so the channel can be used to flood moderator chats and erode trust in the notification system. It is not a direct path to data disclosure or code execution.

## Counterevidence

Actively hunted for a control that would neutralise this. (a) *"Maybe the body flag is ignored server-side"* — no: the handler reads `const actorIsModerator = !!body.actorIsModerator;` and uses it directly in `isModAction`, with no comparison against `auth`. (b) *"Maybe a client-side guard is sufficient"* — the SPA sends `actorIsModerator: isModerator()`, but the server is the trust boundary and the request is a plain `POST` to `/api/bot-notify-training` that any holder of a token can replay; a client-side boolean is not a control. (c) *"Maybe only the actor can be named"* — `actorId` is checked against `auth.id`, but `userIds` is not, so the *victim* named in the text is attacker-chosen and wholly unrelated to the actor. (d) *"Maybe the message is an in-app notification the team ignores"* — no, `bot.notifyModerators` enumerates `role = "moderator" && max_id != ""` and calls `sendBotMessage`, which POSTs to `https://botapi.max.ru/messages?user_id=...`; this is a real MAX messenger message. (e) *"Maybe authorization is enforced upstream by nginx"* — no: nginx forwards `/api/*` custom routes unchanged, as shown by sibling routes returning their own JSON `401`/`403` bodies. (f) The remaining broadcast handlers (`-create`, `-cancelled`, `-restored`, `-status`, `-edit`) **do** carry `auth.getString('role') !== 'moderator'` checks, which confirms this handler's missing check is an oversight rather than intentional design, and that the developers knew the correct pattern. (g) The one genuine constraint found is that `actorId` must equal the caller's own id, so the attacker cannot name an arbitrary *third party* as the moderator — they can only impersonate themselves in a moderator voice. That limits the finding to high rather than critical.

## What Would Change This Severity

Demonstrating that a member can additionally attribute the fabricated action to a named third-party moderator (rather than only to themselves in moderator voice) would raise this to critical, because moderators would then be unable to distinguish impersonated actions from genuine ones at all; conversely, evidence that the moderator chat channel is not operationally relied upon would lower it to medium.

## Technical Analysis

`pb_hooks/bot_notifications.pb.js` registers six bot-notification routes. Five of them (`/api/bot-notify-training-status`, `-edit`, `-cancelled`, `-restored`, `-create`) enforce the moderator role immediately after the authentication check:

```javascript
if (auth.getString('role') !== 'moderator') {
  return c.json(403, { error: 'Forbidden' });
}
```

`POST /api/bot-notify-training` omits that check. It authenticates (`if (!auth) 401`), then reads the behaviour-determining values straight out of the request body:

```javascript
const actorId = body.actorId;
const actorIsModerator = !!body.actorIsModerator;
const totalBookedCount = body.totalBookedCount;
```

The only identity binding applied is `if (actorId !== auth.id) return c.json(403, ...)`. That prevents attributing the message to a *third party*, but it does not restrict what the caller may claim about themselves, which members the message names, or whether the action is rendered with the moderator wording.

The message text is then selected from the attacker-controlled flag (`const isModAction = actorIsModerator && (userIds.length > 1 || userIds[0] !== actorId);`) and delivered with application privileges via `bot.notifyModerators(text)`. `notifyModerators` (in `pb_hooks/botlib.js`) selects recipients with `$app.findRecordsByFilter('users', 'role = "moderator" && max_id != ""', ...)` — bypassing request-scoped rules — and calls `sendBotMessage`, which issues a real `POST https://botapi.max.ru/messages?user_id=<maxId>` carrying the `MAX_BOT_TOKEN`. The effect therefore crosses the trust boundary from an ordinary member into moderator MAX chats, in the club's own bot voice.

The SPA supplies the correct value (`actorIsModerator: isModerator()` in `client/src/services/trainings.js`), which is why the gap is invisible in normal use: it only manifests when the request is issued directly rather than through the UI.

## Proof of Concept

1. Obtain a low-privilege member session (any club member account); confirm its record has `role = "user"`.
2. Send an authenticated `POST /api/bot-notify-training` whose body sets `actorIsModerator` to `true` and whose `userIds` names a *different* member than the caller, with `actorId` set to the caller's own id.
3. Observe `HTTP 200` and `{"success":true}` — the route performs no role check and accepts the caller-supplied moderator flag.
4. The handler renders the message using the moderator wording (`Модератор <actorName> снял <victim> с тренировки ...`) and passes it to `bot.notifyModerators`, which sends a MAX messenger message to every user with `role = "moderator"`.
5. Re-send the same request repeatedly to demonstrate the absence of any rate limit or deduplication; each call delivers another message.

```bash
# Low-privilege member token (role = "user")
TOKEN="<member token>"
ME="hqd42tv9h085bk5"          # caller's own user id (must match the token)
VICTIM="40z6k2wbrnw17wo"      # any other member, attacker-chosen
TRAINING="qs808160ey9ib5q"    # any existing training id

# Fabricated "moderator removed <victim> from the training" broadcast
curl -i -X POST "https://app.milenkih-team.ru/api/bot-notify-training" \
  -H "Authorization: $TOKEN" \
  -H 'Content-Type: application/json' \
  -d "{\"event\":\"unbook\",\"userIds\":[\"$VICTIM\"],\"trainingId\":\"$TRAINING\",\"actorId\":\"$ME\",\"actorIsModerator\":true,\"totalBookedCount\":0}"

# -> HTTP/2 200
# -> {"success":true}
# -> every moderator's MAX chat receives:
#    "Модератор *Николай Кабенюк* снял Илья Миленький с тренировки *<date>* в <time>. Всего записано: 0."
```

## Remediation

1. Derive the moderator flag on the server rather than trusting the request body: replace the `actorIsModerator` read with a check of the authenticated record's `role` field, exactly as the sibling `bot-notify-*` handlers already do.
2. Require the moderator role whenever the request targets members other than the caller; a normal member should only be able to trigger notifications about their own booking. Reject other combinations with `403`.
3. Keep and extend the existing identity binding: validate not only `actorId` but also every id in `userIds` against the caller's permissions for the referenced training.
4. Validate that the referenced training actually exists and that the claimed booking state matches the stored `booked_users` before generating any message, so the notification reflects stored state rather than client-asserted state.
5. Apply a per-user rate limit and short-window deduplication to the notification routes so the moderator channel cannot be flooded.

## Assumptions

Assumes an authenticated low-privilege `user` account (the engagement provides one; any club member has one). The notification setting `training_booking_enabled` must be enabled for the message to be delivered — it is currently `true` on the live instance, and it is a global moderator-controlled toggle rather than a per-user one.
