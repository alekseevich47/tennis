# Session tokens survive refresh and no server-side logout exists

**ID:** vuln-0006
**Severity:** LOW
**Found:** 2026-09-12 15:24:52 UTC
**Target:** https://app.milenkih-team.ru
**CWE:** CWE-613
**CVSS:** 3.1
**Confidence:** High
**Fix Effort:** Medium

## Description

Refresh mints a new token while the previous one keeps working, and there is no logout endpoint, so a captured token stays valid for its full lifetime and users cannot end a session.

## Evidence

A refresh with token T0 returned a different token T1. Both authenticated with HTTP 200. The logout and auth-logout paths both returned 404, and the token was still accepted afterwards.

## Impact

A stolen token remains usable for about seven days with no way for the victim to revoke it, and refreshing does not cut off the old token.

## Counterevidence

No new attack surface on its own. Tokens are revoked on ban via token key rotation and banned records are rejected at the auth hooks, so only the voluntary sign-out path is missing. The token sits in origin-scoped localStorage, so a different user of the same profile does not inherit it.

## What Would Change This Severity

Evidence that the token is additionally reachable by other scripts, such as a confirmed XSS, would raise this.

## Technical Analysis

Tokens are stateless HS256 credentials tied to the record token key rather than server-side session state, so refresh adds a valid credential instead of replacing the old one. The client sign-out only clears the local auth store and never contacts the server. The administrative case is covered by the ban hook, which rotates the token key on ban.

## Proof of Concept

1. Capture a valid token. 2. Call auth-refresh and note the returned token differs. 3. Replay the original token and observe it is still accepted. 4. Attempt both plausible logout endpoints and observe 404.

```scdoc
curl -s -X POST https://app.milenkih-team.ru/api/collections/users/auth-refresh -H "Authorization: TOKEN_T0"
curl -s -o /dev/null -w "status" -X POST https://app.milenkih-team.ru/api/collections/users/auth-refresh -H "Authorization: TOKEN_T0"
curl -s -o /dev/null -w "status" -X POST https://app.milenkih-team.ru/api/collections/users/logout -H "Authorization: TOKEN_T0"

Observed: refresh returned a different token, the original still returned 200, logout returned 404.
```

## Remediation

Add a server-side sign-out endpoint that rotates the record token key, call it from the client sign-out flow, and rotate the token key on each refresh so a refreshed session supersedes the previous credential.

## Assumptions

Requires a pre-existing token compromise.
