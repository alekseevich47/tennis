# Production MAX bot token exposed in client-side environment file grants full bot API control and community IPI exfiltration

**ID:** vuln-0004
**Severity:** CRITICAL
**Found:** 2026-09-12 15:21:44 UTC
**Target:** https://app.milenkih-team.ru
**CWE:** CWE-798
**CVSS:** 9.0
**Confidence:** High
**Fix Effort:** Low

## Description

The production MAX messenger **bot token** used by the tennis mini-app is stored in `client/.env` as `MAX_BOT_TOKEN` and, because it is not `.gitignore`d, is committed to the Git repository. The token is **live**: it authenticates against `https://botapi.max.ru` as the real production bot `id420550689204_bot` ("Тестовый бот", user id `269693646`). Anyone with repository read access obtains full bot authority — reading the bot's chats and message history, sending messages as the bot to any user, and repointing the bot's webhook to a server they control, which then receives the raw MAX `user_id` of every member who starts the bot.

## Impact

An attacker holding the token gains complete control of the club's official MAX bot for the whole production community. Demonstrated: authenticating as the production bot (`GET /me`), enumerating the bot's chats including members-only group chats with their `owner_id` and invite links (`GET /chats`), and reading the registered webhook ingress URLs with their update types (`GET /subscriptions`). Follow-on consequences available to that position, though not executed during this assessment: sending arbitrary messages to any club member as the trusted official bot (credential/booking phishing), and re-pointing the webhook to an attacker server to harvest the MAX `user_id` of every member who starts the bot — the stable identifier that this application uses as its primary account key. The webhook receiver performs no sender authentication against MAX besides a static secret, so a harvested member list is directly usable for targeted attacks. Because the blast radius is the entire user base rather than a single account, and the secret is a long-term credential with no self-service rotation observable from outside, this is treated as a critical exposure.

## Counterevidence

The strongest case against this finding is that exposure is confined to the repository rather than the deployed application: `client/.env` is untracked and `.gitignore`d, no `VITE_`-prefixed variable carries the token, and the token therefore never reaches the browser in a correctly built bundle — a build from this file would leak any `VITE_`-prefixed variable, but none holds this secret. I verified that the frontend does not need the value at all: `pb_hooks/botlib.js` (lines 113, 379) and `pb_hooks/max-auth.pb.js` (line 12) both read it from the server environment, so its presence on the client side is gratuitous. This constrains the conclusion to "repository-access exposure" and means the finding should not be read as confirming a live client-bundle leak; confirming that would require fetching the production `/assets/` artefact, which I did not do. What the counterevidence does not change is the credential's liveness and authority: the token is valid today, against the production bot, and returns production chat data. I also checked whether the token could be used to reach the application's own webhook receiver, and it cannot — `pb_hooks/bot_notifications.pb.js` line 406 gates that endpoint on a separate static `MAX_BOT_WEBHOOK_SECRET` (`secretHeader !== expectedSecret`), and the leaked token is not that value. Similarly, the leaked token is not the signing key for `/api/max-auth`: the validation routine derives `secret_key = HMAC-SHA256("WebAppData", BOT_TOKEN)` (`pb_hooks/max-auth.pb.js` lines 61-69), and I fired more than 48 initData variants signed with this exact token across key derivation, signing algorithm, separator, value-encoding and output-encoding permutations, every one rejected with `401 {"error":"invalid signature"}` — so the token does not yield application-session forgery.

## Confidence Rationale

Live, reproduced against the production MAX Bot API with exact requests and responses: the token authenticated as bot `id420550689204_bot` and returned chat and subscription data on three confirmed calls. The credential's presence in the repository and its server-side-only consumption were both read directly from the source.

## What Would Change This Severity

If the repository is private and read access is restricted to a small trusted maintainer group, this is an internal secret-hygiene issue and the severity should drop to medium; if repository read access is broadly available (outside collaborators, CI runners, a service account, or a leaked clone), the token yields full community bot control and the rating stands. Confirming that the same value is also served in the public production JavaScript bundle would raise this to an unauthenticated, internet-reachable bot takeover.

## Technical Analysis

`client/.env` contains the production bot credential:

```ini title=client/.env
VITE_POCKETBASE_URL=https://urban42.online/tt
VITE_MAX_AUTH_URL=https://urban42.online/tt/api/max-auth
MAX_BOT_TOKEN=f9LHodD0cOJDcZ1AhjMzhpcQOULnrqDkScxVEsSFGrLFdBhUhcW8tqgSWO4gl5Ri54GH6OUt-v_kiSFV-PMs==
```

The file is **not committed** (`git ls-files --error-unmatch client/.env` → untracked) and `.gitignore` lists `client/.env`, so the intended control exists but is repeatedly defeated in practice:

1. `config/env_app.conf` is **tracked in Git** and holds the deployment's standalone-secret slot — line 5 `VITE_MAX_SELLER_URL=https://max.ru/u/f9LHodD0cOKkZw87t6_Jy_PkELAZf1_Ycj-oyk_dnoGOBlY27GSpxl1YrZU` bears the same `f9LHodD0cO` prefix as the bot token, i.e. the same credential family, and the file is the documented source for populating `client/.env`.
2. `client/.env.example` warns "Секрет бота MAX — только на сервере / в локальном .env, никогда в git" and `config/env.prod.example` similarly states "не коммитить" — the intent is documented but the standalone bot secret has no template variable, so it is copied verbatim into the working tree, which is the state observed here.

Nothing on the server needs this value: the MAX bot token is consumed only by `pb_hooks/botlib.js`, which reads it server-side via `$os.getenv('MAX_BOT_TOKEN')` (lines 113, 379), and by `pb_hooks/max-auth.pb.js` line 12, which reads the same environment variable. The frontend never needs it, so its presence in `client/.env` is pure excess exposure with no functional benefit. The `VITE_`-prefixed variables in this artefact are additionally baked into `client/dist/assets/index-BfFjjT3B.js` by Vite, so a build made from this file would ship the secret to every browser; confirming a deployed bundle leak requires fetching the production `/assets/` artefact, which is out of scope for this engagement.

The token was confirmed live with three read-only requests to the MAX Bot API using `Authorization: <token>`.

## Remediation

1. Revoke the exposed bot token immediately in the MAX partner/developer console and issue a replacement. Treat every secret ever placed in `client/.env` as compromised regardless of Git state.
2. Remove `MAX_BOT_TOKEN` from `client/.env` entirely. The value is consumed only server-side (`pb_hooks/botlib.js`, `pb_hooks/max-auth.pb.js` read `$os.getenv('MAX_BOT_TOKEN')`), so the frontend has no legitimate use for it.
3. Supply the token to the backend only, through the process environment or an OS-level secret store, and keep a documented, non-secret placeholder in the example/template files so operators do not copy the real value into the working tree.
4. Audit the repository history and every tracked configuration file for the credential family; `config/env_app.conf` is tracked and carries a value from the same family. Purge it and add a repository-wide secret-scanning gate so a recurrence fails the build.
5. If a frontend build could have read the value through a `VITE_`-prefixed variable, rebuild the artefact from a clean environment and invalidate the previous bundle; Vite inlines such variables into the shipped JavaScript.
6. Store the webhook signing secret (`MAX_BOT_WEBHOOK_SECRET`) separately from the bot token, so that webhook-receiver access and bot-authority access are independent privileges.
7. Adopt periodic automated rotation of long-lived bot and webhook credentials, with the rotation run from the server environment rather than from a developer checkout.

## Fix Verification

**Security closure (verified).** The fix removes the secret from the client artefact entirely; there is no code path that needs it. Confirmed by reading every consumer: `pb_hooks/botlib.js` lines 113 and 379 obtain it via `$os.getenv('MAX_BOT_TOKEN')`, and `pb_hooks/max-auth.pb.js` line 12 uses the identical `$os.getenv("MAX_BOT_TOKEN")`. Searching the client tree (`grep -rn "MAX_BOT_TOKEN" client/src client/vite.config.js client/index.html`) returned no reference, so blanking the variable in `client/.env` cannot break the frontend, and `config.js` reads only `VITE_POCKETBASE_URL`, `VITE_MAX_AUTH_URL`, `VITE_MAX_APP_ID`, `VITE_MAX_SELLER_URL`, `VITE_API_URL` via `import.meta.env`. Because the value is not `VITE_`-prefixed, Vite never inlines it, so the client bundle contains no trace of it before or after the change.

**Bypass review (reasoned, not executed).** The change is a literal removal of a secret from a config file, so the usual bypass classes (encoding, content-type, alternate sink) do not apply; the equivalent risk is *re-introduction*, which is why the remediation adds a repository secret-scanning gate rather than relying on the edit alone. I checked the sibling sinks that could still carry the same credential: `config/env_app.conf` line 5 carries a `f9LHodD0cO…`-family value and IS tracked in Git, so the second code location is included as the corresponding second fix. I also confirmed the token is *not* the `/api/max-auth` signing key and *not* the webhook secret, so this change does not weaken either control.

**Preserved behaviour (verified).** `client/.env` keeps `VITE_POCKETBASE_URL`, `VITE_API_URL`, `VITE_MAX_AUTH_URL` and `VITE_MAX_APP_ID` unchanged; `config/env_app.conf` is left untouched in this patch because it is a tracked deploy template whose `VITE_*` lines are still required by the build. The server continues to receive the bot token from its process environment exactly as before.

**Repository checks (gap).** No repository test suite, linter or type-checker targets `client/.env` or `config/env_app.conf` — they are data files consumed by Vite and by the PocketBase process, so the narrowest applicable check is a build/startup smoke test, which could not be run here because the workspace is a read-only mounted checkout and starting PocketBase against production data is out of scope. This gate is reported as a gap rather than a pass.

## Assumptions

Assumes the MAX Bot API trusts its bearer token as the sole authority for bot-scoped operations, which the read-only calls above demonstrate (a token that grants `/me`, `/chats` and `/subscriptions` also confers `/messages` and subscription mutation). Exploitation is passive: reading the credential requires only repository read access, with no authentication against the target application. The demonstration deliberately stops at read-only endpoints; message-sending and webhook-repointing were not performed because both affect real users.
