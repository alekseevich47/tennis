# Wildcard CORS on PocketBase API allows cross-origin reads with a bearer token

**ID:** vuln-0005
**Severity:** LOW
**Found:** 2026-09-12 15:23:20 UTC
**Target:** https://app.milenkih-team.ru
**CWE:** CWE-942
**CVSS:** 3.1
**Confidence:** High
**Fix Effort:** Low

## Description

The API returns a wildcard Access-Control-Allow-Origin together with authorization advertised as an allowed request header, for any origin.

## Evidence

A preflight from https://evil-attacker.example returned HTTP 204 with Access-Control-Allow-Headers authorization, Access-Control-Allow-Methods GET,HEAD,PUT,PATCH,POST,DELETE and a wildcard Access-Control-Allow-Origin. A cross-origin authenticated GET returned HTTP 200 with a wildcard origin and real member records in the body.

## Impact

Any JavaScript running in a victim browser can read API responses carrying the victim token and exfiltrate them.

## Counterevidence

Access-Control-Allow-Credentials is absent on every response tested, so browsers do not attach cookies cross-origin and no cookie-based CSRF exists here. The session is header-borne and no application cookie carries authority. The exposure is conditional on the victim token already being readable by JavaScript and on the attacker obtaining script execution, both of which presuppose a separate weakness. Scored as a defence-in-depth weakness rather than an authentication bypass.

## What Would Change This Severity

Demonstrating a concrete script-execution path in the origin would raise severity, since it would turn this into a direct token-exfiltration chain.

## Technical Analysis

PocketBase default CORS middleware answers any origin with a wildcard and echoes requested headers and methods. nginx adds no CORS policy of its own, so nothing narrows it before it reaches the browser.

## Proof of Concept

1. Send a CORS preflight from an attacker origin requesting the authorization header. 2. Observe the 204 response advertising a wildcard origin and authorization as an allowed header. 3. Repeat against another route to confirm it is a server-wide default. 4. From the attacker origin issue the token-bearing request the preflight authorised and read the body.

```python
curl -si -X OPTIONS "https://app.milenkih-team.ru/api/collections/users/records" -H "Origin: https://evil-attacker.example" -H "Access-Control-Request-Method: GET" -H "Access-Control-Request-Headers: authorization"
```

## Remediation

Replace the wildcard origin with an explicit allowlist, stop advertising authorization to unlisted origins, and restrict allowed methods per route.

## Assumptions

A victim holds a valid session token in localStorage and the attacker can make the victim load attacker-controlled JavaScript.
