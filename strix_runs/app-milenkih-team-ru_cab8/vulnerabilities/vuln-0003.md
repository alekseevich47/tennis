# Cross-user training history forgery via unrestricted `moderator_kicked_users` / `unbooked_users` writes (PocketBase `trainings` PATCH)

**ID:** vuln-0003
**Severity:** MEDIUM
**Found:** 2026-09-12 15:19:49 UTC
**Target:** https://app.milenkih-team.ru
**Endpoint:** /api/collections/trainings/records/{id}
**Method:** PATCH
**CWE:** CWE-863
**CVSS:** 6.5
**Confidence:** High
**Fix Effort:** Low

## Description

Any authenticated low-privilege user can write an arbitrary other member's ID into the `moderator_kicked_users` and `unbooked_users` relation fields of any training record via `PATCH /api/collections/trainings/records/{id}`. The server-side guard `applyBookingSideEffects` only validates `booked_users` and `attended_users` (throwing `403 "Можно записать только себя"`), so these two fields accept foreign user IDs without any ownership check. The forged entries persist and render in other members' training history as the moderator-attributed badge "Снят модератором" (removed by moderator), falsifying club attendance records visible to moderators.

## Impact

An authenticated ordinary club member can falsify any other member's training history on any training (past, present, or closed), making that member appear to have been removed from a training by a moderator. The forged badge "Снят модератором" and the training entry are rendered in that member's profile and in the moderator's member-profile view (`ProfileViewModal` / `ProfilePage`, via `getTrainingStatusForUser`). Because these fields are also consumed by booking eligibility and reporting logic, an attacker can inject spurious "kicked"/"unbooked" markers into other members' records at will. Every training in the instance is affected, and the write succeeds even on trainings where the attacker is not a participant. This is a cross-user integrity violation of records the business treats as authoritative attendance history.

A second effect of the same root cause is that the attribution mechanism distinguishing a moderator removal from a system removal is also attacker-selectable: `restore_insufficient_users` drives `pb_hooks/trainings_audit.pb.js` to log a removal as a system action rather than a moderator action.

A third effect of the same root cause is that the moderator-only guard on attendance marking can be switched off for a request by supplying `is_cancelled`. The authorization block containing the `attended_users` check is conditioned on transition flags derived from that caller-supplied value, and the exempted branch reaches `adjustAttendanceCountTx`, which writes the server-authoritative `users.attendance_count` with no authorization check. That counter feeds the achievement engine (`client/src/services/achievements.js`, `pb_hooks/achievementslib.js`, and the `profile.achievement.grant` audit path). The counter increment could not be persisted during this assessment because the only reachable training had already ended, which gates that adjustment off — a data-dependent proof gap rather than a control — so it is recorded as a control failure with the persisted effect unproven.

## Counterevidence

The strongest case against this finding is that the affected fields might be entirely cosmetic and never influence a security decision. I tested that: `moderator_kicked_users` is read by `client/src/features/profile/ProfileViewModal.jsx` and `ProfilePage.jsx` to compute the displayed training status and badge, and by `client/src/features/admin/stats/StatsTrainingsCountModal.jsx` to expand training records; `restore_insufficient_users` is consumed by `pb_hooks/trainings_audit.pb.js` to attribute a removal to the system. So the values do drive both display and audit attribution. I also verified the write is not an artifact of a single training or of an unusual record state: it succeeded on all three trainings in the instance, including closed past ones, and with an explicit negative control (`booked_users` with the same ID returns 403). I confirmed that the values are durably stored by reading the record back after the write, and that referential integrity is enforced (invalid or malformed IDs are rejected with 400), so this is limited to writing real member IDs into these fields rather than injecting arbitrary strings. I did not observe any change to the victim's membership counters (`available_sessions`, `unpaid_sessions`, `used_sessions`, `attendance_count` all remained unchanged), so this is an integrity falsification of attendance records rather than a financial or session-quota impact — which is why it is rated a cross-user integrity issue rather than critical.

## What Would Change This Severity

Confirmation that club standings, membership billing, or tournament seeding are derived from these fields would raise the severity, as would a moderator-facing report that consumes `moderator_kicked_users` for capacity or eligibility decisions. Separately, a single end-to-end reproduction against a not-yet-ended training showing `users.attendance_count` incremented through the exempted restore branch would raise the severity by demonstrating a write to a server-authoritative statistic that drives achievement levels. Confirmation that the write is restricted to trainings the caller participates in would lower it.

## Technical Analysis

The `trainings` collection update rule is `@request.auth.id != ""`, so any authenticated user may PATCH any training. Field-level authorization is delegated entirely to the JSVM hook `pb_hooks/trainings_booking_validate.pb.js`, which calls `trainingslib.assertTrainingUpdateAllowed` (field allow-list) and then `trainingslib.applyBookingSideEffects` (ownership check + side effects).

`assertTrainingUpdateAllowed` treats five fields as user-editable for non-moderators (`TRAINING_USER_EDITABLE`, `pb_hooks/trainingslib.js:304`): `booked_users`, `unbooked_users`, `unpaid_booked_users`, `moderator_kicked_users`, `restore_insufficient_users`. It therefore permits the update to proceed.

`applyBookingSideEffects` (`pb_hooks/trainingslib.js:394`) then enforces ownership **only** for four collections computed by `audit.newlyAdded` / `audit.newlyRemoved`:

```javascript title=pb_hooks/trainingslib.js startLineNumber=394 endLineNumber=412
  // --- IDOR (C-6): обычный пользователь — только себя; посещаемость — только модератор ---
  if (!isCancelTransition && !isRestoreTransition) {
    if (added.length && !isModerator) {
      for (i = 0; i < added.length; i++) {
        if (String(added[i]) !== authId) {
          throw new ForbiddenError('Можно записать только себя');
        }
      }
    }
    if (removed.length && !isModerator) {
      for (i = 0; i < removed.length; i++) {
        if (String(removed[i]) !== authId) {
          throw new ForbiddenError('Можно снять с записи только себя');
        }
      }
    }
    if ((attendedAdded.length || attendedRemoved.length) && !isModerator) {
      throw new ForbiddenError('Отметка посещения — только модератор');
    }
  }
```

`added`/`removed` are derived solely from `booked_users`, and `attendedAdded`/`attendedRemoved` solely from `attended_users`. There is **no validation of `unbooked_users`, `moderator_kicked_users`, `unpaid_booked_users`, or `restore_insufficient_users`**. Writing a foreign user ID into `moderator_kicked_users` produces `added`/`removed`/`attendedAdded`/`attendedRemoved` that are all empty, so `hasWork` is false and the function returns without complaint — the record is saved with the attacker-controlled value.

**Control-failure variant (same root cause).** The entire authorization block above is itself conditioned on two flags computed from the incoming record:

```javascript title=pb_hooks/trainingslib.js startLineNumber=387 endLineNumber=395
  var isCancelTransition = !original.getBool('is_cancelled') && record.getBool('is_cancelled');
  var isRestoreTransition = original.getBool('is_cancelled') && !record.getBool('is_cancelled');
  ...
  // --- IDOR (C-6): обычный пользователь — только себя; посещаемость — только модератор ---
  if (!isCancelTransition && !isRestoreTransition) {
```

Because both flags derive from the caller-supplied `is_cancelled` value, a member can select the branch that skips the attendance check as well as the self-only checks. The exempted restore branch calls `adjustAttendanceCountTx(txApp, restoreAttended[i], 1)` (`:489-493`), which sets `users.attendance_count` and saves with no authorization. That write runs inside `$app.runInTransaction`, so it does not re-enter the `users` `onRecordUpdateRequest` hook and therefore never passes through the field-level ACL in `pb_hooks/users_access_guard_lib.js`. `assertTrainingUpdateAllowed` does not compensate, because `attended_users` is present in `TRAINING_COMPARE_FIELDS` but absent from `TRAINING_USER_EDITABLE`, so it is rejected only while that same transition conditional allows the block to run. Two independent controls are gated by one caller-controlled expression and fail together.

Git history confirms the structure is long-standing: `git show 5ea0b5b:pb_hooks/trainingslib.js` (v0.39) already contains the same wrapper plus the same restore-branch call; the only later commit touching the hook (`efaa612`, v1.0.18) inserted `assertTrainingUpdateAllowed` in front of it without addressing the derived-flag precondition.

**Downstream consequence of the forged fields.** `pb_hooks/trainings_audit.pb.js` uses `moderator_kicked_users` and `restore_insufficient_users` to interpret a removal: `addedInsufficient` populates `insufficientSet` and causes the event to be logged as a system action ("Система сняла ... (недостаточно посещений)"), while other foreign removals are attributed to a moderator (`booking.booking.cancel_moderator`).

Client-side, `client/src/features/profile/ProfileViewModal.jsx:59` and `ProfilePage.jsx:53` compute the training status directly from `moderator_kicked_users`:

```javascript title=client/src/features/profile/ProfileViewModal.jsx startLineNumber=59 endLineNumber=63
function getTrainingStatusForUser(training, userId) {
  const kicked = training.moderator_kicked_users || [];
  if (kicked.includes(userId)) return 'kicked';
  if (!hasTimeRangeEnded(training.date, training.duration || 0)) return 'booked';
  return (training.attended_users || []).includes(userId) ? 'attended' : 'missed';
}
```

with `kicked` mapped to the badge label "Снят модератором". The attacker therefore controls how another member's attendance is presented.

## Proof of Concept

Setup: authenticate as an ordinary `user` (not moderator). Obtain a second, unrelated member's user ID from `GET /api/collections/users/records`.

1. Confirm the legitimate cross-user booking guard rejects `booked_users` writes (negative control): send `PATCH /api/collections/trainings/records/{trainingId}` with body `{"booked_users":["<victimId>"]}` and observe `403 {"message":"Можно записать только себя."}`.
2. Send the same PATCH with the victim's ID placed in `moderator_kicked_users` instead. The server returns `200` and persists the value.
3. Send the same PATCH with the victim's ID in `unbooked_users`. The server returns `200` and persists the value.
4. Read the record back with `GET /api/collections/trainings/records/{trainingId}` and observe the victim's ID stored in `moderator_kicked_users` and `unbooked_users`.
5. Repeat step 2 against every other training record to show the write is not scoped to trainings the attacker participates in.
6. Clean up by PATCHing the original values back.

    data = json.dumps(body).encode() if body is not None else None
    req = urllib.request.Request(
        BASE + path, data=data, method=method,
        headers={"Authorization": TOKEN, "Content-Type": "application/json"})
    try:
        with urllib.request.urlopen(req, timeout=40) as r:
            return r.status, r.read().decode()
    except urllib.error.HTTPError as e:
        return e.code, e.read().decode()

# Negative control: the guarded field is correctly rejected
print(call(f"/api/collections/trainings/records/{TRAINING}",
           "PATCH", {"booked_users": [VICTIM]}))
# -> (403, '{"data":{},"message":"Можно записать только себя.","status":403}')

           "PATCH", {"moderator_kicked_users": [VICTIM]}))
# -> (200, '{"...","moderator_kicked_users":["i9l04znh39u9iy4"],...}')

           "PATCH", {"unbooked_users": [VICTIM]}))
# -> (200, ...)

# Read back: the forged entry is durably stored

## Remediation

Extend the non-moderator ownership check in the trainings update hook so that every relation field the allow-list exposes to ordinary users is validated against the caller's own ID, not only `booked_users` and `attended_users`.

1. In `applyBookingSideEffects`, additionally compute the added/removed sets for `unbooked_users`, `moderator_kicked_users`, `unpaid_booked_users`, and `restore_insufficient_users`, and require every added or removed identifier to equal the authenticated user's ID for non-moderators. Reject with the existing `ForbiddenError` otherwise.
2. Alternatively, remove the moderator-semantic fields from the ordinary-user allow-list entirely. `moderator_kicked_users` and `restore_insufficient_users` represent moderator decisions and should not be writable by a plain user under any transition; ordinary users only need to add/remove themselves from `booked_users` (and their own `unbooked_users` entry that accompanies it).
3. Make the authorization block independent of the cancel/restore transition. The flags `isCancelTransition` and `isRestoreTransition` are derived from the caller-supplied `is_cancelled` value and currently wrap the whole ownership and attendance check, so a caller can select the branch that skips them. Derive any transition handling from the persisted record, or apply the ownership and attendance checks unconditionally and treat the transition only as a side-effect selector.
4. Treat `users.attendance_count` and the other membership counters as protected state. Updates performed with application privileges inside a transaction bypass the `users` field-level ACL, so any such write should assert the actor's authority explicitly at the point of the write rather than relying on the hook on the `users` collection.
5. Add a server-side regression test that performs the foreign-ID PATCH described in the PoC and asserts a `403` for each of the four relation fields, including on trainings where the caller is not a participant, plus a case asserting that a non-moderator cannot change attendance through a cancel/restore-shaped request.

Because this issue is exploitable purely through direct API calls (bypassing the SPA), it cannot be mitigated with client-side changes.

## Assumptions

Requires only a valid authenticated session for any member account with role `user`; no moderator privileges, no victim interaction, and no knowledge of the victim beyond their user ID (obtainable from the authenticated `users` list endpoint). Assumes the default deployment, where the trainings update rule is `@request.auth.id != ""` and field authorization is enforced exclusively by the reviewed hook.
