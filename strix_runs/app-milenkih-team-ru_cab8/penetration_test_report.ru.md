# Отчёт о тестировании на проникновение

**Сгенерирован:** 2026-09-12 15:42:35 UTC

# Краткое резюме

Проведена авторизованная оценка мини-приложения теннисной секции **«Секция Миленьких»** (`https://app.milenkih-team.ru`) в комбинированном режиме white-box (обзор исходников только на чтение) и black-box (тестирование живого API) с учётной записью обычного участника. Подтверждено восемь валидированных находок, одна из них — критическая.

**Общий уровень риска: повышенный (Elevated).** Приложение — React Mini App, напрямую работающее с бэкендом PocketBase (Go/SQLite); отдельного application-сервера перед БД нет, поэтому каждое правило коллекции и каждый JSVM-хук — это производственная граница безопасности. Команда явно вложила усилия в эти контроли: учёт сессий бронирования, лимиты мест, входные данные достижений, проверка подписи MAX-аутентификации, гейты модераторских маршрутов и медиа-прокси выдержали целенаправленные атаки и были зафиксированы как «исключены» с указанием конкретного контроля. Остаточный риск исходит из двух мест: **секрет, который не является секретом**, и ряд **контролей, написанных непоследовательно** на соседних (sibling) путях кода.

**Ключевые находки**

1. **Critical — раскрыт production-токен MAX-бота.** Живой credential бота лежит в `client/.env` в рабочей копии и присутствует в истории Git репозитория. Он аутентифицирует запросы к MAX Bot API как настоящий production-бот, давая чтение инвентаря чатов, возможность отправлять сообщения любому участнику от имени официального бота и возможность перенаправить webhook бота. Это самый важный пункт для устранения.
2. **High — неаутентифицированный доступ к медиа участников.** Файловые эндпоинты PocketBase отдают загруженные участниками фото и видео без аутентификации, а кастомный маршрут `/api/video-poster` — единственный обработчик в проекте вообще без authentication gate.
3. **Medium (×3) — непоследовательная авторизация на путях записи.** Участник может подделать историю тренировок других участников, отключить guard авторизации посещаемости для своего запроса, передав transition-поле, имитировать модераторские уведомления через незащищённый notification-маршрут и писать metric-строки через collection-эндпоинт, обходя собственную валидацию приложения.
4. **Low (×3) — пробелы hardening.** Wildcard CORS, session-токены, остающиеся валидными после refresh при отсутствии logout, и правило уведомлений, позволяющее пользователю переадресовать своё уведомление другому участнику.

**Бизнес-влияние.** Токен бота — наивысший бизнес-риск: это официальный канал коммуникации клуба; контроль над ним позволяет убедительный фишинг каждого участника, а также сбор стабильных идентификаторов участников, которые приложение использует как ключи аккаунтов. Остальные находки — проблемы целостности и конфиденциальности внутри клубного сообщества (поддельные записи посещаемости, поддельные официальные уведомления и получение приватных медиа), а не компрометация финансов или инфраструктуры.

**Тема remediation.** Находки не архитектурные. Каждая устраняется тем, что уже существующий контроль применяется ко всем его call path: один отсутствующий authentication gate в маршруте, у которого 34 sibling-а его уже имеют; одна проверка модератора, пропущенная в маршруте, где пять sibling-ов её выполняют; один список relation-полей, который не расширили при написании ownership-проверки; и одно правило валидации, живущее на маршруте, а не в хранилище данных.

**Замечание по валидации.** Самый ценный незакрытый пункт — потенциальная эскалация находки с токеном бота: если подпись MAX Bridge удастся воспроизвести с утёкшим токеном, раскрытие превратится в полный захват аккаунта каждого участника, а не только в полномочия отправки сообщений от бота. Конструкция подписи атаковалась интенсивно и не была воспроизведена, поэтому это честно зафиксировано как открытый proof gap с конкретным следующим шагом, а не как finding.

# Методология

**Тип engagement.** Комбинированная white-box (исходники) и grey-box/black-box (живой API) оценка, авторизованная владельцем приложения.

**Область**

- Живое приложение: `https://app.milenkih-team.ru` (React 18 + Vite SPA, бэкенд PocketBase 0.23, внутри webview мессенджера MAX).
- Исходники на обзоре (только чтение, файлы не изменялись): `client/src` (services, hooks, рендереры ленты), `pb_hooks/*` (все JSVM-хуки и кастомные маршруты), `schema.json` (экспорт правил коллекций), `config/*` (nginx и конфигурация деплоя).
- Вне области и не тестировалось: legacy-деплой `urban42.online`, массовые рассылки реальным пользователям и разрушающая модификация production-данных.

**Стандарты.** Тестирование организовано вокруг **OWASP API Security Top 10 (2023)** и **OWASP Top 10 (2025)** и выполнялось по фазам в стиле **PTES** с тест-кейсами **OWASP WSTG** для веб-слой приложения.

**Подход**

1. **Разведка и картирование.** Живое исследование поверхности API (`/api/collections/*`, `/api/files`, `/api/realtime`, кастомные hook-маршруты `/api/*`) в сочетании с полным чтением экспорта схемы и каждого скрипта `pb_hooks`, с построением инвентаря правил по коллекциям и полного инвентаря кастомных маршрутов.
2. **Threat modelling.** Общая модель угроз выведена из исходников и живого поведения: attacker-controlled входы, граница operator/moderator, инварианты, которые должны держаться, и калибровка severity для этого деплоя.
3. **Параллельное специализированное тестирование.** Работа разложена на сфокусированные потоки, каждый отвечает за одну поверхность: горизонтальная object-level авторизация и field-level over-exposure по всем коллекциям; логика бронирования тренировок и учёта сессий; целостность достижений, рейтинга и статистики (включая client-side расчёт прогресса); injection, шаблоны и outbound-запросы в hook-слое; аутентификация, сессии и CORS; React-рендеринг и client-side trust; broken function-level authorization по всем 35 кастомным маршрутам.
4. **Negative controls на всём протяжении.** Каждый отказ сопровождался positive control, доказывающим, что эндпоинт достижим и отказ дал именно контроль, а не сеть. Поддельные JWT, cross-user записи, traversal-payloads, loopback SSRF-цели и варианты admin-маршрутов отрабатывались против их подлинных аналогов.
5. **Полная валидация каждой находки.** Findings воспроизводились вживую с сырыми request/response доказательствами до включения в отчёт. Кандидаты, которые не удалось закрыть, явно фиксировались как открытые proof gap, а не «закрывались» допущением.
6. **Обзор chaining.** Оценивались комбинации находок; одна существенная комбинация вынесена как открытый пункт с конкретным следующим шагом (см. Технический анализ).

**Покрытие.** Зафиксировано 75 surface-level оценок: 15 закрыты как reported, 33 — как ruled out с именованным контролем в конкретном месте, 18 — tested with no issue found, 1 — not applicable, 8 — unresolved follow-ups. Тестирование охватило все 18 content-коллекций, слой аутентификации и сессий, слой раздачи файлов, все 35 кастомных hook-маршрутов, React rendering pipeline и конфигурацию деплоя.

**Соблюдённые ограничения.** Исходные файлы не изменялись. Production-записи не уничтожались; каждая тестовая запись откатывалась и проверялась, где API это позволял; ни один broadcast-эндпоинт не вызывался в сторону реальных пользователей. Остаются и раскрываются два пункта test-hygiene: небольшое число инертных строк `content_views`, которые non-superuser удалить не может, и восстановление поля участника, временно изменённого во время пробы.

# Технический анализ

**Модель severity.** Оценки отражают продемонстрированное следствие proof of concept, а не категорию слабости. Там, где high-impact исход блокировался подтверждённым ограничением, рейтинг снижался, а ограничение фиксировалось, вместо того чтобы отбрасывать finding. Там, где сбой контроля был продемонстрирован, но его персистентный эффект — нет, finding сообщался на уровне продемонстрированного с явным указанием gap.

## Находки

**1. Production-токен MAX-бота раскрыт в клиентском environment-файле (Critical, CWE-798).** Живой credential бота хранится в `client/.env` и присутствует в истории Git репозитория. Он аутентифицирует к MAX Bot API как production-бот (`id420550689204_bot`) и использовался для чтения инвентаря чатов бота и зарегистрированных webhook-подписок. С ним атакующий может отправлять сообщения любому участнику голосом бота клуба и перенаправить webhook на свой сервер, чтобы собирать стабильные идентификаторы участников, которые приложение использует как ключи аккаунтов. Секрет потребляется только на сервере (`$os.getenv('MAX_BOT_TOKEN')` в `botlib.js` и `max-auth.pb.js`), поэтому его присутствие на клиентской стороне — это раскрытие без функциональной пользы.

**2. Неаутентифицированный доступ к приватным медиа участников (High, CWE-306).** Медиа content-коллекций доступны без какой-либо аутентификации. Независимо от этого `GET /api/video-poster` — единственный кастомный маршрут в проекте без проверки аутентификации; он резолвит записи с привилегиями приложения и затем стримит байты с диска. Эксплуатация требует известного идентификатора записи и сохранённого имени файла, которые анонимно не перечисляются — именно из-за этого ограничения оценка High, а не Critical.

**3. Подделка чужой истории тренировок и отключаемый attendance guard (Medium, CWE-863).** Правило update коллекции `trainings` позволяет любому аутентифицированному участнику писать в любую тренировку, а field-level авторизация делегирована хуку. Этот хук открывает ordinary-участникам relation-поля с модераторской семантикой (`moderator_kicked_users`, `restore_insufficient_users`), проверяя ownership только для `booked_users` и `attended_users`, поэтому участник может записать чужой идентификатор и тем самым влиять на отображение посещаемости и атрибуцию удалений в audit trail. Тот же хук оборачивает весь блок авторизации — включая moderator-only assertion посещаемости — в условие, выведенное из caller-supplied значения `is_cancelled`, поэтому guard можно выключить для запроса; освобождённая ветка доходит до незащищённой записи в server-authoritative счётчик `users.attendance_count`, обходя field-level ACL, потому что запись выполняется с привилегиями приложения внутри транзакции. Инкремент счётчика не удалось персистировать на доступных данных — этот gap указан в finding, а не «свёрнут» в рейтинг.

**4. Broken function-level authorization на маршруте уведомлений о тренировке (Medium, CWE-862).** `POST /api/bot-notify-training` аутентифицирует вызывающего, но никогда не проверяет роль модератора и берёт флаг «acting as moderator» и список затронутых участников из тела запроса. Поэтому участник может заставить бота клуба доставить сообщение, представляющее действие модератора против названного участника, в чат каждого модератора. Все пять sibling notification-маршрутов выполняют проверку роли; этот — нет.

**5. Обход валидации записи метрик (Medium, CWE-602).** Приложение валидирует вход view-tracking на своём dedicated-маршруте, но нижележащая коллекция остаётся напрямую записываемой через generic record API при лишь self-attributed правиле. Значения, которые приложение отвергает, принимаются через collection-эндпоинт, а поскольку у коллекции нет delete-правила для non-superuser, получившиеся строки навсегда неудаляемы. Потребители — только модераторы и пере-резолвят объекты на сервере, что ограничивает impact.

**6–8. Пробелы hardening (Low).** Wildcard CORS на API объявляет authorization header как разрешённый cross-origin request header (модель bearer-токена и отсутствие `Access-Control-Allow-Credentials` предотвращают классический CSRF, но украденный токен становится usable с любого origin). Session-токены остаются валидными после refresh, server-side logout нет — захваченный токен жертва отозвать не может. Правило update `notifications` позволяет участнику переадресовать своё уведомление другому участнику, включая forged in-app уведомления; контент проходит sanitizer, поэтому impact — spoofing, а не выполнение скрипта.

## Что устояло

Несколько контролей атаковались и подтверждены как исправные — это существенный контекст для приоритизации. Валидатор подписи MAX Bridge реализует спецификацию корректно и отверг более 60 поддельных вариантов payload. Слой auth-токена отверг algorithm confusion, подмену claim и просроченные токены. Каждый из 35 кастомных маршрутов, кроме отмеченного выше, проверяет роль до любого side effect, а поддельные moderator claims игнорируются в пользу persisted-роли. Учёт сессий тренировок, лимиты мест и race-поведение проверялись concurrent-burstами и остались согласованными. User field-level allow-list корректно отвергает self-service изменения rating, attendance, membership и ban. Медиа- и Yandex.Disk-прокси отвергли loopback, metadata-service, `file://` и host-suffix-confusion цели. Server-side persistence достижений нет, а входы, которым доверяет client-side расчёт достижений, — moderator-only. React pipeline рендеринга постов и комментариев использует allow-list sanitizer; stored XSS не найден; в задеплоенных бандлах секретов нет, source maps не отдаются.

## Цепочки атак (attack chaining)

Комбинации находок оценивались. Finding о spoofed-уведомлениях поглощается раскрытием bot-токена (владелец токена может писать любому участнику напрямую), поэтому не складывается в больший impact. Notification-reassignment и notification-route findings относятся к одному классу эффекта без аддитивности. **Одна комбинация существенна и остаётся недоказанной:** подпись MAX Bridge строится с ключом, производным от bot-токена, поэтому владелец токена имеет материал для подписи launch-параметров — что превратило бы раскрытие токена в authentication forgery любого аккаунта участника. Это атаковалось интенсивно, key derivation сервера воспроизведена точно, принятой подписи не получено; byte-string, который подписывает живой бэкенд, не удалось восстановить из его же исходников без подлинного captured sample. Зафиксировано как highest-value открытый пункт с конкретным следующим шагом, а не как finding, потому что не продемонстрировано.

## Системные темы

- **Control drift между sibling-ами.** Две наиболее impactful authorization-находки — случаи контроля, который существует и работает на большинстве call path, но пропущен на одном: маршрут среди 34 sibling-ов, проверка роли среди шести sibling-ов, список relation-полей, не расширенный вместе с ownership-проверкой. Review, diff-ящий sibling-обработчики, поймал бы все из них.
- **Валидация на маршруте, а не в хранилище данных.** Поскольку клиенты говорят с БД напрямую, проверка в кастомном маршруте не является свойством данных. Это механизм обхода записи метрик и причина, по которой media-правила разошлись с экспортом схемы.
- **Секреты в client-side environment-файле.** Credential бота не имеет client-side потребителя, но живёт в client environment-файле, откуда попал в version control. Устойчивое исправление — gate secret-scanning в репозитории.

# Рекомендации

## Немедленно (эта неделя)

1. **Отозвать и перевыпустить MAX bot token.** Считать раскрытое значение скомпрометированным. Удалить из `client/.env` и вычистить из истории Git, затем проаудитить каждый tracked configuration-файл на ту же credential family. Добавить repository secret-scanning gate, чтобы повтор ломал сборку.
2. **Добавить отсутствующий authentication gate на `GET /api/video-poster`,** зеркалируя проверку, которую уже делают sibling-обработчики, и ставить её до резолва записи и любого доступа к файловой системе.
3. **Сверить live-правила коллекций с экспортом схемы.** Медиа отдаются без аутентификации, тогда как экспорт объявляет authenticated-only view rules; выяснить, дрейфовал ли deployed ruleset или посредник расширил доступ, и сделать intended rule явным в схеме, чтобы хранилище само его enforced.
4. **Добавить отсутствующую проверку роли модератора на `POST /api/bot-notify-training`** и перестать доверять флагу acting-as-moderator из тела запроса.

## Краткосрочно (этот месяц)

5. **Сделать авторизацию тренировок независимой от transition.** Убрать условие cancel/restore вокруг ownership- и attendance-проверок, чтобы вызывающий не мог выбрать ветку, которая их пропускает; любую обработку transition выводить из persisted-записи. Применить ownership-проверку ко всем relation-полям, которые открывает allow-list, либо полностью убрать moderator-semantic поля из этого allow-list.
6. **Перенести валидацию на хранилище данных.** Ограничить создание `content_views` server-side кодом или добавить collection-level create hook с той же валидацией, что у application-маршрута, и дать коллекции путь удаления или retention job.
7. **Ужесточить write path уведомлений.** Требовать `recipient = @request.auth.id` на update и заморозить поле recipient; предпочтительно server-side создание, чтобы вызывающие не выбирали получателя.
8. **Ограничить CORS** origin-ом самого приложения вместо объявления authorization для любого origin.
9. **Обеспечить отзыв сессии.** Реализовать server-side logout, инвалидирующий выданные токены, и инвалидировать предыдущий токен при refresh.

## Среднесрочно (этот квартал)

10. **Пересмотреть read-доступ к записям участников.** Коллекция `users` полностью читаема любым аутентифицированным участником, включая contact и membership поля, которые интерфейс для других не показывает. Ввести field-level visibility, чтобы API возвращал только то, что нужно каждому view.
11. **Добавить rate limiting и de-duplication** на маршруты view-tracking и audit-click, чтобы ограничить write amplification с одного аккаунта, и на медиа-эндпоинты, чтобы enumeration идентификаторов был непрактичен.
12. **Принять практику sibling-diff review** для authorization-кода: когда контроль добавляется в один обработчик, требовать подтверждения, что sibling-ы и call path несут его тоже. Повторяющийся класс находок в этом engagement — контроль, корректный везде, кроме одного места.
